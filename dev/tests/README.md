# The checks

    dev/tests/run.sh              everything
    dev/tests/run.sh --no-page    everything but the headless browser

Needs `python3`, `node` and a chromium. Nothing from a package manager, and nothing here reaches a network.

**These run here, on the machine the change was made on.** Z, 2026-09-20: *"We will test only if it builds there. All the other tests should be on this machine."* A GitHub runner is asked one question, in `.github/workflows/build.yml`: does the source still build, and build the same twice. Everything below is run before a change is handed over, and what it found is said with the change.

**This does not decide whether a release is good.** `dev/CHECKLIST.md` is what decides that, and a person runs it against a real card. What this does is notice when something that used to work has stopped, which is the part a person cannot do after every change. It was built on 2026-09-20, when Z judged the page ready to ship and asked for it; before that there was deliberately none, because a suite the agent writes and runs is the agent vouching for itself.

## How the leak duration is checked, in three places

`Dur.` is the one figure on the page that is not a reading of a signal, so it gets the most attention:

- **`card-vs-answer.js`** adds up the samples above zero from the loaded signal and compares that with `answer.json`, and then checks each run above zero against where the card put it -- above zero at its first and last sample, at zero on either side of it. The case `on-and-off-leak` exists for this: twelve runs, six at zero and six above it, alternating, no two of them the same length and each of the six levels its own -- one at half a liter a minute, because PAPvault sets no threshold of its own, and one running to the end of the recording, where there is no sample after it. It comes to 118 minutes of a five-hour night, so a reader that returned the running time is out by an hour and a half.
- **`cards/derived.js`** does the same rule at a finer alternation, by writing physical zero over the leak of every second record of a committed case.
- **`page/run.py`** reads the Leak box out of the rendered page. The other two re-implement the rule they are checking; this one reads what the page itself worked out, which is the only one of the three that can see the rule in `src/app.js` change.

## How the derived cards work

Every case in `dev/synthetic/out` is a night the machine stamped in one go, so one rule had no case that could fail on it. `cards/derived.js` therefore builds cards from the committed ones: it moves a file's stamp and its header start together, cuts a file's records down with its header, or writes physical zero over half a signal through the file's own calibration. The answers stay known by construction, because what was changed is known.

**The break cards are written down, not worked out.** `make-break-cards.js` lists what CPAP day each session must land on and why, beside the moment it is stamped at. Nothing there re-implements the rule: a check that computed the day the way the reader computes it would agree with the reader whatever both of them did.

They are built into `dev/tests/out/`, which git ignores, and rebuilt on every run.

## Each check was shown to fail

A check that cannot fail is not a check. These were each broken on purpose and seen to fail:

- taking the annotation back to being an event's start rather than its end, which is what the page did until Z checked a real card on 2026-09-23: `card-vs-answer.js` reported 86 mismatches, every one off by exactly the duration of the event it names. The parser check stayed green, correctly -- it reads where the annotation sits, which did not move;
- totalling a group's nights instead of averaging them, by dropping the division in `meanOf`: the range probe reported `(36, 7.2)` -- the five nights added up against their mean;
- drawing a night of flow a sample at a time again, by raising `REDUCE_ABOVE` in `src/plots.js` past any card: the pyramid probe reported 3 failures and printed the size of it -- **720,000 points** against the 2,814 the reduction draws;
- putting the 2026-09-23 failure back, by slicing each level to the window on screen before handing it over: 2 failures, and they are the two checks that exist for it. After a zoom the series covered 10,086 seconds against a window of 10,088, which is the whole of what "the data followed the scale" means;
- telling the summary stack a grouped point is a single night, `grouped` becoming `false` in `src/app.js`: the grouped probe reported 3 failures, the weekly, monthly and yearly charts each calling their bars `Hours` where they are a mean per day. Daily stayed green, correctly, since there a bar is one day's hours;
- zooming by a fixed factor per wheel event again, instead of by the distance the event reports: the wheel probe reported 1 failure, one notch and two notches both coming to **0.800**. That is the defect in one number -- twice the distance, the same zoom -- and on a trackpad, which sends a couple of hundred events for one pinch, it made the window shrink by `0.8^231`;
- deciding which of the page and the plot a wheel gesture belongs to on every event instead of once, which is how a sideways swipe was built and removed on 2026-09-23: the wheel probe reported 2 failures, and they are the two checks written for it -- a sideways event arriving inside a gesture the page already had took it back and slid the window 776 seconds;
- padding a grouped chart's scale by half a day rather than half a step, which is what the page did until 2026-09-24 and what Z reported as bars cut down the middle: the grouped probe reported 10 failures, and the pixels named it -- weekly drew its end bars 16 and 15 wide against a middle bar of 25, monthly 25 and 24 against 41. **Daily stayed green**, because there half a day *is* half a step, which is why the defect was only ever visible in a grouped view;
- averaging a group's sessions instead of counting them, which is what the page did until Z changed it on 2026-09-24, and formatting a grouped point as a plain date again: the grouped probe reported 6 failures, three of each, and **daily stayed green for both** -- with one night to a group a mean and a total are the same number, and its reading was a date to begin with. Weekly read `17.30` sessions against the card's `108`, and `Nov 10, 2025` against `Week of 2025/11/10`;
- taking the week out of the grouping, so a week is each night on its own: 2 failures, the weekly level drawing 5 points where it must draw 1, and its value being one night rather than the five averaged;
- measuring the break from where a session's files stop rather than from where its flow stopped, `endOf()` in `src/card.js` becoming `session.end`: `cards/derived.js` reported 1 failure, the second session of `break-from-flow` landing on the day before the one it must have. **`day-boundary.js` reported 33 checks and 0 mismatches**, because it hands `flowEnd` in itself, and that is the whole reason that card exists;
- turning the break rule off on a card rather than in a made-up session list, `DAY_BREAK_MINUTES` becoming 0: `cards/derived.js` reported 3 failures, the second, third and fourth sessions of `bathroom-break` moving to the next day while the first, which the 6 o'clock cut decides on its own, stayed where it was;
- moving the limit from noon to eleven, `DAY_BREAK_BEFORE_HOUR` becoming 11: 1 failure, and it is the session stamped at 11:59 -- the one Z asked for on 2026-09-24, which carries *because* it is a minute short of the limit. Nothing else on either card moved, so that session is the only thing holding the limit's upper side up;
- moving the day cut from 6 to 5: `day-boundary.js` reported 9 mismatches;
- turning the break rule off, by making `DAY_BREAK_MINUTES` 0 in `src/card.js`: `day-boundary.js` reported 9 of its 33, and every night the rule must leave alone -- one unbroken session, a mask-off break in the middle of the night, a morning nap hours later, two nights running -- still passed;

- the earlier ones are recorded where they were found, in `.claude/development-notes/drawing-the-plots.md`.

**One of those runs is worth keeping in mind.** With the day cut moved to 5 o'clock, `card-vs-answer.js` still passed all 822 checks. Every session in the committed cases begins at an hour where a 5 o'clock cut and a 6 o'clock cut agree, so the reader suite cannot see the boundary move at all; only `day-boundary.js` can. That is not a gap in the suite, though: `day-boundary.js` exercises the rule directly, at every edge it has. It is a fact about which check earns its keep -- the smallest one here is the only one that can see the cut move.

**The same is true of the break rule, and there it is a gap.** Every session in the committed cases begins in the evening or between midnight and 6, so none of them has a break that crosses the cut, and turning the rule off changes no card and no `answer.json`. `day-boundary.js` exercises it directly, but nothing that comes off a card does. The case that would is proposed in `dev/synthetic/resmed-cases.md` as `bathroom-break` and waits for Z.

## The marker check, and what it deliberately does not assert yet

Every synthetic card carries `SYNTHETIC-DO-NOT-DISPLAY-7Q4Z` in each field that would name a person or a machine. `page/run.py` now searches the whole rendered document and all of local storage for it, which passes: those fields live in EDF header bytes 8 to 167 and in `Identification.tgt`, and PAPvault reads neither.

It does **not** cover the name of the folder the card came from. That name is shown, on purpose: Z settled it on 2026-09-21 by saying what the page does rather than changing it, since the name is what tells a reader which folder they actually opened. `CLAUDE.md` and the manual both say so now, including that it goes along with a screenshot of that dialog. Running the probe with the marker as the folder name -- `python3 dev/tests/page/make-marker-probe.py . <out> SYNTHETIC-DO-NOT-DISPLAY-7Q4Z` -- makes the check fail and names `folder-status`, which is how it was shown to be able to fail, and which would be the standing check if that decision ever went the other way.

## Hand tools, which `run.sh` does not call

Two scripts here assert nothing. They print what `src/card.js` makes of a card, which is what you want when a real card is behaving in a way no check explains. They were written while working out what a session is, and they are kept because that question will come back.

    node dev/tests/cards/sessions-of.js . <card dir> [expected count]
    node dev/tests/cards/samples-of.js  . <card dir>

The first lists every session with its day, its start and end, its kinds of file, and which stamps it was built from. The second loads each session and prints how many samples and how much span each signal came out with, which is how a dropped file shows up. Neither is in `run.sh`, so neither can fail a run.

**Two more like them are not here.** `card-shape.py` and `session-gaps.py` printed the shape of a real card -- how many recordings a day folder holds, how long the gaps between them are, what a session count would be at each threshold -- from file names and headers only, with no date and no value in the output. They lived in a session scratchpad, which is not durable, and they are gone from this machine. If a real card needs diagnosing again they belong here, next to these two.

## What it does not cover

- **Anything about a real card.** Only Z has one, and no real data ever reaches these.
- **Whether a figure is the right figure.** The suite checks that the reader agrees with the generator. Both were written here, so where a fact came from one source, the suite cannot be the check on it -- `dev/READING-LOG.md` says where each fact came from.
- **Oximetry**, which is turned off and has no card to test against.
- **How it looks.** Layout is checked only where it can be measured: that a stack shares one plotting area, that a count sits to the right of its bar, that the sticky bar is drawn over the plots, that each width of the layout puts the cards, the calendar and the bar's buttons where that width says. Whether it reads well is Z's eye.
- **Any width under 500 pixels.** Headless Chromium clamps a window to 500 css pixels and reports that width back, so the narrowest thing the probes can open is the width the menu arrives at. A phone at 320 is `dev/CHECKLIST.md`'s `narrow-columns`, in a browser's responsive mode. What the probes can do without a narrow window is squeeze a card and fire the window's own resize event, which is how the chart floor is reached.
- **The menu's animation.** The probes read where the panel is anchored, not where it is drawn: a CSS transition does not advance under virtual time, so the panel is measured mid-slide. That it fades in at all is Z's eye.
